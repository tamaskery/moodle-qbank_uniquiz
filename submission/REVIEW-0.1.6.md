# Review of the earlier robustness findings against 0.1.6

Reviewed 11 October 2026 against `0559a8cfa46932bb7ef2b7ddffeb502e169eaf76`. This is a focused source review and assessment of existing regression coverage, not an independent security audit. The grading corrections are separate from these findings. No additional runtime changes were made for this review.

| Finding | Exists in 0.1.6? | Is a fix needed? |
| --- | --- | --- |
| 1. Unbounded `defaultgrade` | Yes. The server and browser require a finite positive mark but impose no upper bound. Moodle's question schema uses number(12,7). Existing PHPUnit and HTTP fixtures use `1e100` to prove late rollback and a content-free HTTP 500. | Recommended before production: validate a documented, database-safe mark range in both browser stages and the server, returning 422. This is a robustness/UX defect, not an authorization bypass. Replace the overflow-based late-failure fixture with an independent induced core failure so rollback coverage remains meaningful. The current beta retains this known limitation. |
| 2. Tags allegedly capped at 50 | No. `TAG_MAX_LENGTH` is 255 in the actual Moodle 4.5, 5.2 and 5.3 branches. `PARAM_TAG` truncates to that constant, and the browser/README use 255 code points. | No change to 50 is needed; it would introduce an unnecessary restriction. The unchanged-cleaning requirement remains correct. This check does not certify every Unicode whitespace edge case. |
| 3. Reusable failed token / session lock | Yes. The hash/result are saved only after success, permitting correction and retry; there is no attempt counter. Moodle's session lock is retained during import. The 120-second helper requests an execution allowance, not a guarantee that every failed request runs that long. | Optional hardening. A per-token counter alone is easy to bypass by opening a fresh wizard and can block legitimate corrections. If abuse is observed, design a session/user-level work or rate budget, count expensive attempts, preserve successful replay, and test expiry/concurrency. Existing per-request caps and capability checks reduce exposure; this is not an anonymous import path. |
| 4. Receipt eviction | Yes. At 50 non-expired receipts, `array_shift` removes the oldest regardless of success or an open browser tab. This can invalidate an old unused token or remove a successful retry receipt. | Recommended reliability follow-up before broad rollout. Expiry is already applied first. Preferring unused receipts protects successful replay but can still evict a token being edited in another tab; it does not fully solve active-tab handling. Define that policy explicitly and test 50/51 receipts, expiry and retries. Same-session import requests are serialized, so index.php cannot evict a token halfway through a locked import. |
| 5. Markup in plain-text fields | Partly. Names and Short Answer accepted text can contain literal markup text. Numerical values must match the finite-number grammar; True/False text must be exactly `true` and `false`, so script-style values in those two answer types are already rejected. Nested XML elements are rejected everywhere. | Clarify SECURITY.md; no blanket HTML encoding of Short Answer values. Encoding them would change answers such as `a<b`. Names use Moodle's native plain-text formatting, and Short Answer values rely on core's escaping/filtering at each display surface. Preserve literal values and include those surfaces in staging tests. |
| 6. Most tests outside installable ZIP | Yes, intentionally. The ZIP includes 11 PHPUnit tests and one Behat scenario; the public repository supplies the engine, HTTP, browser, adversarial and translation harness plus its CI workflow. Existing PHPUnit already tests validation-to-HTTP status mapping, log redaction, permissions and late rollback. | No packaging fix required. Keep build dependencies and disposable-site credentials outside the installable ZIP. Extracting receipt policy into a small testable service and adding PHPUnit policy tests would improve coverage when that policy changes; actual HTTP/session/concurrency behaviour still merits the external harness. |
| 7. Unpaginated categories | Yes. Every category in permitted contexts is loaded, its hierarchy labelled, sorted and rendered into a select. | Optional scalability work. No measured failure on the target site is available. Benchmark thousands of categories, then consider an authorized searchable selector and cache/precompute hierarchy labels. Server destination capability validation must remain. |
| 8a. Mutable static validator context | Yes. `prepare()` resets question/field at entry; synchronous request use does not currently re-enter it. | Optional refactor, not a demonstrated release defect. Move diagnostics to an instance/context if recursive validation or long-lived concurrent execution is introduced. Test context reset after failures. |
| 8b. Category-marker error numbering | Yes. A category marker inherits `count + 1`, which can point at the next actual question or beyond the final question. | Small diagnostic fix recommended; use document/category-marker location without consuming a question number. It does not alter validation or imported questions. |

## Overall assessment

The tag-length concern is disproved, and the plain-text concern is narrower than reported. The mark bound and receipt-eviction policy deserve targeted follow-up; category-marker numbering is a minor diagnostic correction. The other items are optional hardening, coverage, scalability or maintainability work. None of these findings establishes an authorization or injection hole or requires abandoning the verified beta candidate. They do not waive staging acceptance before production use.
